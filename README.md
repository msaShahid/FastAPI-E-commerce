# FastAPI E-commerce

A production-ready e-commerce backend built FastAPI,
PostgreSQL, SQLAlchemy 2.x (async) and Alembic.

## What's in it

- **Auth** -- JWT access + refresh tokens with rotation and refresh-token
  reuse detection (a replayed token revokes its whole family), role-based
  access (user / admin).
- **Catalogue** -- categories and products, search / filter / sort /
  pagination, image upload (JPEG, PNG, WebP; the file's real contents are
  checked, not just its name or `Content-Type`).
- **Cart and checkout** -- guest carts (cookie) and user carts, guest or
  logged-in checkout, idempotent checkout (`Idempotency-Key` header), stock
  reserved under a row lock so concurrent buyers can never oversell.
- **Orders and payments** -- order status workflow, Stripe payments with
  webhook handling and refunds, and a script
  (`scripts/cancel_stale_orders.py`) that cancels unpaid orders after a
  timeout and returns their stock to inventory.
- **Addresses**, **GraphQL** endpoint at `/graphql`, and an **audit log**
  of admin actions.
- **Operational basics** -- Redis-backed rate limiting (register 5/min,
  login 10/min, refresh 20/min per IP), explicit-origin CORS, security
  headers, environment-based configuration.

## Running locally

Copy `.env.example` to `.env` and fill in the values (the real `.env` and
`.env.production` hold credentials and are git-ignored -- never commit them).
Then:

```bash
docker compose up --build
docker compose exec api alembic upgrade head   # create / update the tables
```

Then visit:
- http://localhost:8000/health
- http://localhost:8000/docs (Swagger UI, auto-generated by FastAPI)

Services started by `docker-compose.yml`: `api`, `db` (PostgreSQL),
`redis` (rate limiting), `test_db` (used by the tests) and `adminer`.
`docker-compose.prod.yml` is the production variant; it expects external
managed PostgreSQL and Redis configured through `.env.production`.

## Stopping

```bash
docker compose down
```

To also wipe the database volume:

```bash
docker compose down -v
```


### Recreate API Container

If you update `.env` or change API environment variables, recreate the API container so the changes are loaded:

```bash
docker compose up -d --force-recreate api
```

## Tests

```bash
docker compose exec api pytest
```

The suite covers the services and the real HTTP API (auth, products,
categories, image upload, cart, guest checkout, GraphQL), plus concurrency
tests that run many buyers at once against a few units of stock. The tests
build their tables from the models (`Base.metadata.create_all`) on a separate
test database; they never touch your development data.

## Database migrations

Schema changes go through Alembic:

```bash
docker compose exec api alembic upgrade head                            # apply
docker compose exec api alembic revision --autogenerate -m "describe it"  # new migration
docker compose exec api alembic check                                   # models vs. database
```

`alembic check` must say "No new upgrade operations detected." If you change a
model, generate a migration for it; CI fails the build when the models and the
migrations disagree. Review every autogenerated migration before committing
it -- autogenerate cannot see everything.

## Continuous integration

`.github/workflows/ci.yml` runs on every push to `main` and every pull
request, as four separate jobs:

| Job | What it checks |
|---|---|
| Lint (ruff) | `ruff check .` |
| Tests (pytest) | the full suite, against real PostgreSQL and Redis service containers |
| Migrations (alembic) | `alembic upgrade head` on an empty database, then `alembic check` (no drift between models and migrations) |
| Dependency audit (pip-audit) | known vulnerabilities in dependencies; two reviewed `python-jose` advisories are ignored, with the reasoning documented in the workflow |

CI uses throwaway credentials and never touches real data.

## Load testing

`loadtest/` contains a Locust script that simulates browsing shoppers plus

## Creating the first admin user

Registration (`POST /api/v1/auth/register`) always creates a regular user, and
promoting someone to admin (`PATCH /api/v1/users/{id}`) requires you to
already be logged in as an admin. On a brand-new database there is no admin
yet, so nothing can grant the first one through the API itself.

`scripts/bootstrap_admin.py` is the escape hatch for exactly that. Unlike
`scripts/seed.py` (which refuses to run when `ENVIRONMENT=production`,
because it creates fixed, publicly-known test credentials), this script is
meant to be run against a real production database.

```bash
docker compose exec api python -m scripts.bootstrap_admin --email admin@yourcompany.com
```

- If that email doesn't exist yet, you'll be prompted (input hidden) for a
  password, then the account is created and promoted to admin in one step.
- If that email already belongs to an existing user, it's promoted to admin
  in place -- no password needed.
- It always asks for a y/n confirmation before writing anything; pass
  `--yes` to skip that for non-interactive use (e.g. a deploy step), and set
  the password via the `ADMIN_BOOTSTRAP_PASSWORD` environment variable
  instead of the interactive prompt in that case.
- Safe to run more than once against the same email -- it just reports the
  current state instead of erroring.

See the top of `scripts/bootstrap_admin.py` for full usage details.

## CORS

Allowed cross-origin callers are controlled by `CORS_ORIGINS`, an explicit
list of origins -- never a wildcard. This matters here specifically because
the API is called with credentials (cookies, `Authorization` headers), and
`CORSMiddleware` is configured with `allow_credentials=True`; pairing that
with a wildcard origin doesn't work anyway (browsers refuse to expose a
credentialed response to page JS when the allowed origin is `*`), so
`Settings` rejects `"*"` in `CORS_ORIGINS` outright at startup instead of
leaving that failure mode to be discovered later against a real browser.

Set it as a JSON array in your `.env` (or `.env.production`):

```bash
CORS_ORIGINS=["https://shop.yourcompany.com","https://admin.yourcompany.com"]
```

A comma-separated string is **not** accepted -- pydantic-settings parses a
list-typed setting from its environment variable as JSON, so anything else
fails validation at startup rather than silently allowing the wrong origins.

## Pre-commit hooks

Hooks run automatically on `git commit` and block it if something is wrong,
so problems are caught on your machine before they ever reach CI. They check
**staged files only**, so they never rewrite files you didn't touch.

What runs: `ruff` (lint, with safe auto-fixes), `ruff format`, a secrets
scanner (`detect-secrets`), private-key detection, a 500 KB file-size limit,
a merge-conflict-marker check, a YAML syntax check, and a guard that refuses
real `.env` / `.env.production` files.

One-time setup, from the project root (on your own machine, not inside Docker):

```bash
pip install pre-commit
pre-commit install
```

Notes:

- If `ruff format` reformats a file, the commit is stopped on purpose. Run
  `git add` on the changed files and commit again.
- `detect-secrets` compares against `.secrets.baseline` (known, reviewed
  findings such as the demo key in the playground router and the throwaway
  CI values). Test files are not scanned. If it flags something that is
  genuinely harmless, add `# pragma: allowlist secret` to that line, or
  accept it into the baseline with
  `detect-secrets scan --baseline .secrets.baseline`.
- To run every hook against the whole repo at any time: `pre-commit run --all-files`.
  The first run will reformat many existing files; commit that as its own
  "apply ruff format" change.
